# Change feeds and geofence events

KFM can refresh a device marker, camera link, or zone occupancy when a transaction
commits. Each feed contains committed row changes, with complete before/after
images. Geometry values in event images are canonical WKT strings.

```sql
CREATE TABLE devices (id INT PRIMARY KEY, name TEXT, geom GEOMETRY);
CREATE TABLE cameras (id INT PRIMARY KEY, device_id INT);
CREATE TABLE zones (code TEXT, geom GEOMETRY);

INSERT INTO zones VALUES
  ('Assembly', ST_MakeEnvelope(0, 0, 10, 10)),
  ('Warehouse', ST_MakeEnvelope(10, 0, 20, 10));

CREATE CHANGEFEED map_edits ON devices, cameras;
CREATE GEOFENCE occupancy ON devices(geom) ZONES zones(geom);

INSERT INTO devices VALUES (1, 'CAM-01', ST_Point(5, 5));
BEGIN;
UPDATE devices SET geom = ST_Point(15, 5) WHERE id = 1;
INSERT INTO cameras VALUES (101, 1);
COMMIT;
```

The last commit produces a device `update` and camera `insert` in `map_edits`.
`occupancy` produces `exit` Assembly followed by `enter` Warehouse. The four
events have the same commit sequence and timestamp. A rollback produces none.
Geofences are feeds in the same namespace; read and subscribe using their names.

```sql
DROP CHANGEFEED occupancy;
DROP CHANGEFEED map_edits;
```

Create/drop feeds outside a transaction. Names must be unique, watched tables
must exist, and geofence columns must be declared `GEOMETRY`. Quoted identifiers,
comments, and a trailing semicolon are supported. Each management call accepts
exactly one statement. Drop all dependent feeds before replacing or dropping a
watched table. The internal `__nexus_changefeed_log` name is reserved.

## Event contract

| Field | Meaning |
| --- | --- |
| `feed` | Changefeed or geofence name |
| `sequence` | Durable, increasing global event cursor |
| `commit_sequence` | Shared by all events generated by one watched commit |
| `timestamp_ms` | Time assigned while preparing the commit, UTC milliseconds since Unix epoch |
| `table`, `row_id` | Table and stable synthetic row identity |
| `operation` | `insert`, `update`, `delete`, `enter`, or `exit` |
| `old`, `new` | Complete row images; absent side is `None`/null |
| `zone` | For geofences: zone table, stable row ID, and zone row values |

Synthetic IDs survive updates, deletion of earlier rows, and reopen. They are
independent of the storage engine's vector offsets and do not assume a column
named `id` is a primary key. Primary key columns remain available in the row
images. Identical duplicate rows get distinct IDs. IDs are scoped to a watched
table's lifetime; dropping every dependent feed ends that lifetime.

Like SQLite sessions, a transaction combines repeated edits to the same row:
the first before-image and final after-image form one event per row per row feed.
Insert then update becomes an insert; update then delete becomes a delete;
insert then delete and edits that restore the original row produce no event.
Changes appear in first-touch statement order and table row order. Multiple row
feeds receive their own event copies in feed-name order. `INSERT OR REPLACE`
uses deletion/insertion identities when it actually replaces a row. Unchanged
rows generate no event. A feed does not backfill rows that existed at creation.

`sequence` is global across feeds, so gaps within one feed are normal. Commits
that do not change watched data need not advance `commit_sequence`. All row
events precede geofence events in a commit. Within each geofence, all exits
precede all enters, ordered by device row ID and zone row ID. Intermediate
positions inside a transaction are not reported.

## Boundary and zone semantics

Membership uses **`ST_Covers(zone.geom, device.geom)`**. A point on a wall is
inside. A point on the shared wall between adjacent zones is inside both zones;
moving from A's interior to B's interior emits exit A then enter B in one commit.
Overlapping zones can both contain a device. Polygon hole interiors are outside;
their boundaries are inside. NULL, empty geometries, and incompatible SRIDs do
not establish membership, matching the existing scalar function's behavior.

Inserts and deletes can enter or exit a zone. Edits to zone geometry, zone
inserts, and zone deletes re-evaluate stationary devices too. Membership is
compared between the transaction's starting and final states, even when both
tables change. Metadata-only edits do not emit membership events. On exit,
`zone.values` describes the old zone; on enter, it describes the new zone.
Device `old`/`new` can be identical when only the zone moved.

## Rust

```rust,no_run
use nexusql::NexusSQL;
use std::time::Duration;

# async fn example() -> nexusql::Result<()> {
let db = NexusSQL::new("./kfm").await?;
db.set_changefeed_retention(20_000)?;

// None reads all currently retained events. Some(n) reads strictly AFTER n.
let events = db.changes("map_edits", Some(42))?;
for event in events {
    // Apply the event idempotently; save event.sequence after applying it.
    println!("{} {}", event.sequence, event.operation.as_str());
}

// Atomically attach a cursor, catch up, then block for subsequent commits.
// None subscribes at the current head, with no historical replay.
let mut stream = db.subscribe("occupancy", None)?;
// These are blocking APIs; use spawn_blocking when consuming from Tokio.
let next = tokio::task::spawn_blocking(move || {
    stream.recv_timeout(Duration::from_secs(5))
}).await.unwrap()?;
# Ok(())
# }
```

`ChangeSubscription` also implements `Iterator<Item = Result<ChangeEvent>>`,
`recv()` and `try_recv()`. Subscription attachment and log publication use one
lock, so catch-up cannot race with a commit and miss an event. Subscriptions
retain their database/log handle; drop them before reopening the same disk path.

## Python

Build with `maturin develop` in `bindings/python`.

```python
from nexusql import NexusDB

with NexusDB("./kfm") as db:
    db.set_changefeed_retention(20_000)
    for event in db.changes("map_edits", since=42):
        print(event["operation"], event["old"], event["new"])
        # Apply the map update, then durably save event["sequence"].

    stream = db.watch_changes("occupancy")  # future commits
    event = stream.recv(timeout=5.0)       # seconds; None on timeout
    if event:
        print(event["operation"], event["zone"]["values"]["code"])
    del stream
```

`watch_changes(feed, since=n)` replays events after n before waiting. It is also
a blocking iterator (`next(stream)` / `for event in stream`). Waiting releases
the GIL so another Python thread can commit. Supply a timeout to `recv` when the
application needs periodic cancellation checks. Feed errors raise `RuntimeError`.

## Retention, durability, and integration

The default global retention limit is **10,000 event rows**, configurable through
`set_changefeed_retention`. The positive limit, definitions, sequence counters,
row identities, and retained events persist in the versioned internal table
`__nexus_changefeed_log`. This table uses the existing compressed/chunked storage;
it is hidden from normal table loading. There is no time-travel query support.

Trimming removes the oldest event rows, including part of a large commit if
necessary to respect the exact bound. Explicit cursors older than the last
trimmed event **for that feed** fail with an expired-cursor error. Take a fresh
application snapshot and establish a new cursor when this happens. Reading with
`since=None` deliberately returns the retained tail without promising completeness.
Live subscriptions use cursors over the same bounded log; a slow consumer gets
the same expiry error instead of an unbounded queue or silent loss. Dropping a
feed invalidates its subscriptions and removes its history. Recreating a name
does not revive old subscriptions. Persist each event cursor after applying the
event, and make consumer updates idempotent for reconnect/retry delivery.

The **single post-commit notification call** is `PreparedCommit::post_commit`
inside `DurableExecutor::commit_dirty`. Both SQL DML and the native fast/direct
bulk insertion path capture successful row changes before this commit boundary.
The feed module prepares the next log table without publishing it, and
`DiskStorage::commit_tables` writes that table **together with all dirty user
tables in the same WAL transaction**. After that call succeeds, publication is
infallible: it swaps the prepared journal into memory and wakes subscribers.
A journal lock spans preparation, persistence, and publication, so retention
changes and subscriber attachment cannot race with a prepared log version.

Rows, geometry, feed events, retention trimming, sequence counters, and stable
row identities therefore recover together. An incomplete WAL transaction exposes
neither its data nor its events. In the default FULL sync mode, successful
commits have synced both to disk before notifying consumers. NORMAL and OFF
retain the WAL's documented weaker sync guarantees; see
[disk durability](../development/durability.md). There is no separate post-commit
feed write or data/event crash window.

Failed statements and failed bulk autocommits restore both their table and their
tentative feed capture, including row IDs and cursors. Any earlier deferred bulk
changes remain pending. A failed explicit COMMIT keeps its transaction active;
ROLLBACK discards the pending row images and events without notifying subscribers
or writing a feed record. WAL I/O failure poisons the writer until reopen. An I/O
error during sync may leave an uncertain commit: recovery determines whether the
complete commit marker survived, and data and events resolve together. A failed
commit never publishes tentative events on the current handle.

`set_bulk_mode(true)` defers autocommit data **and events** until `flush()` or an
explicit commit boundary. Disabling bulk mode alone does not publish. BEGIN first
commits the preceding deferred batch; explicit COMMIT publishes its own batch.
Flush or checkpoint inside an active transaction does not publish its events.
Explicit shutdown rolls back an active transaction and flushes deferred
autocommits. This applies to feed notifications in memory databases as well.
Feed DDL first commits any preceding deferred batch and requires autocommit.
Retention-setting changes commit only their metadata/log update, without flushing
pending user data; they are rejected during an active SQL transaction.

`tests/changefeed_test.rs` inspects actual WAL redo payloads to assert that device,
camera, and feed-log keys share one commit. It exits a child without Drop or
checkpoint, checks recovery at frame/payload boundaries and every byte of the
final commit marker, and verifies that later uncommitted device/zone edits never
appear. Read-only WAL fault injection in `transaction::durable::changefeed_tests`
checks SQL/bulk autocommit failures, explicit COMMIT failure followed by rollback,
and preservation of earlier deferred captures. Python tests also cover failed
bulk validation, deferred publication, rollback, and reopen.

The current implementation captures watched tables and checks every device/zone
pair for changed geofences. Its cost is O(devices × zones) per relevant commit,
and it rewrites the retained log table. This favors KFM's modest datasets and
keeps storage/transaction changes isolated. The integration test reports a
1,000-device/two-zone commit measurement; it is a debug correctness fixture,
not a production throughput benchmark.

Design reference: SQLite's public-domain session extension,
`ext/session/sqlite3session.c` (`xPreUpdate` registration and changeset
before/after images). This implementation is original Rust. It reuses NexusQL's
existing `ST_Covers`; no PostGIS or GEOS source was copied.
